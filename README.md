# 거북AI 동기화 (A단계)

Notion → 로컬 SQLite. 봇이 질문을 받을 때 Notion API를 때리지 않게 만드는 계층.

## 왜 실시간 조회를 안 쓰는가

Notion `search` API는 키워드 매칭이라 "토스파 레시피"에 약하고, 초당 3회 한도에 걸린다.
디스코드에서 질문이 몰리면 그대로 병목이 된다. 미리 긁어와서 로컬에서 답한다.

## 설치

```bash
pip install -r requirements.txt
cp .env.example .env      # 토큰 채우기
python sync.py --doctor   # 설정/권한 점검
```

`--doctor` 는 토큰 유효성과 **DB별 접근 권한을 따로따로** 확인한다.
통합 연결을 빠뜨리면 에러 없이 조회가 0건으로 나오기 때문에, 이 점검을 먼저 통과하고
넘어가는 편이 빠르다.

### 토큰이 없다고 나올 때

1. `.env` 가 `sync.py` 와 같은 폴더에 있는지 (다른 위치면 `GOBUK_ENV_FILE` 로 지정)
2. `.env.example` 의 `secret_xxxx` 자리표시자를 실제 값으로 바꿨는지
3. 셸에 이미 `NOTION_TOKEN` 이 export 되어 있으면 그쪽이 우선한다 (`.env` 가 덮어쓰지 않음)

### 조회가 0건으로 나올 때

토큰은 맞는데 결과가 비어 있다면 거의 항상 **통합 연결 누락**이다.
4개 DB를 각각 풀페이지로 열고 `···` → 연결 → 통합 추가.
DB마다 따로 해줘야 하며, 상위 페이지에만 걸어두는 것으로는 부족한 경우가 있다.

## 실행

```bash
python sync.py --doctor       # 설정 점검
python sync.py                # 증분. 크론 10~30분 주기
python sync.py --full         # 전체 + 삭제 정합. 하루 1회
python sync.py --reflatten    # API 없이 로컬 재생성 (답변 문구 수정 시)
python sync.py --stats        # 적재 현황
python query.py "토스파 레시피 알려줘"
python smoke_test.py          # 토큰 없이 로직 검증
```

크론 예시:

```
*/15 * * * *  cd /opt/gobuk_sync && python sync.py    >> sync.log 2>&1
30   4 * * *  cd /opt/gobuk_sync && python sync.py --full >> sync.log 2>&1
```

## 구조

| 파일 | 역할 |
|---|---|
| `config.py` | 데이터소스 등록부. DB 추가는 여기부터 |
| `notion_api.py` | REST 래퍼. 레이트리밋, 페이지네이션, 본문 수집 |
| `flatten.py` | 원시 행 → `answer_text` / `search_text` |

| `embed.py` | OpenAI 임베딩 (변경분만) |
| `sync.py` | 오케스트레이션 |
| `query.py` | 검색 검증 도구. B단계 라우터의 뼈대 |

## 설계상 중요한 지점

### 1. 답변을 미리 완성해둔다

`answer_text`에 사람이 읽을 수 있는 완성 문장이 들어간다.

```
**토마토 스파게티** — 요리사 레벨 12 / 조리대에서 제작
재료: 밀 3개, 토마토 4개, 치즈 1개, 소금 1개
결과: 토마토 스파게티 2개
효과: 공격력 +8%, 15분 지속
```

정형 질문은 이걸 그대로 내보내면 된다. **LLM 호출 0회, 응답 즉시, 오답 확률 0.**
메모리뱅크보다 토큰 절감 효과가 크다.

### 2. 참조 전파 (`ripple_stage`)

아이템 "토마토"의 이름을 바꾸면 그걸 재료로 쓰는 레시피의 답변 문구가 낡는다.
그런데 레시피 행 자체는 수정된 적이 없어서 `last_edited_time` 증분 쿼리에 안 잡힌다.

`depends_on`에 참조한 페이지 ID를 저장해두고, 변경분의 피참조 레코드를 찾아
로컬 원본으로 다시 만든다. **API 호출은 발생하지 않는다.**

### 3. 원본 프로퍼티 보관 (`raw_props`)

답변 포맷을 바꿀 때 Notion을 다시 긁을 필요가 없다. `--reflatten` 한 방이면 끝.
전체 재수집은 rate limit 때문에 오래 걸리므로 이 차이가 크다.

### 4. 게시취소 vs 삭제

`상태` 필터를 서버 쪽에 걸지 **않는다.** 걸어버리면 `게시 → 검수중`으로 내려간 행이
쿼리에 안 잡혀서 로컬에 계속 남는다. 전부 받아서 로컬에서 판단한다.

삭제는 다르다. 지워진 페이지는 애초에 결과에 안 나오므로 증분으로는 못 잡는다.
`--full`의 전체 ID 대조가 이 역할을 한다. 하루 1회는 꼭 돌려야 한다.

### 5. 캐시 무효화 신호 (`change_log`)

B단계 메모리뱅크가 읽을 표. 레시피가 바뀌면 그 페이지를 근거로 만들어진 캐시 답변을
지워야 한다. 안 그러면 패치 전 정보를 계속 뱉는다.

```sql
SELECT page_id, change FROM change_log WHERE consumed = 0 ORDER BY id;
-- 캐시 정리 후
UPDATE change_log SET consumed = 1 WHERE id <= ?;
```

### 6. 별칭 색인 (`aliases`)

정규화된 별칭 → 페이지 ID 역색인. B단계에서 **임베딩 유사도만으로 캐시를 히트시키지
않기 위한 검증 장치**로 쓴다.

"토마토스파게티 레시피"와 "크림스파게티 레시피"는 임베딩상 0.96 이상으로 붙지만,
고유명사 정확매칭을 필수 조건으로 걸면 절대 섞이지 않는다.

## 벡터DB를 왜 안 썼나

거북스토리 규모(수천 행)에서 numpy 전수 코사인은 수 ms에 끝난다.
Chroma/Qdrant를 붙이면 운영 대상만 하나 늘어난다. 수만 행을 넘어가면
`chunks` 테이블만 옮기면 되고, 그 외 코드는 손댈 필요 없다.

한국어 FTS는 기본 토크나이저가 조사 때문에 잘 안 맞아 `trigram`을 썼다 (SQLite 3.34+).

## 알려진 한계

- `relation`이 25개를 넘으면 Notion이 잘라서 준다. 현 스키마(재료 슬롯 1개씩)에서는
  안 걸리지만, 다대다 관계를 추가하면 `__TRUNCATED__` 마커를 확인해야 한다.
- 본문 표 블록은 파싱하지 않고 경고만 남긴다. 표로 정리할 정보면 DB여야 한다.
- 이미지 안의 텍스트는 읽지 못한다. 기획자에게 "스크린샷에 정보 담지 말 것"을
  반드시 전달할 것.
- 조사 제거는 규칙 기반이라 완벽하지 않다. 별칭 사전이 이를 상당 부분 보완하지만,
  누락이 잦으면 `kiwipiepy` 같은 형태소 분석기를 붙이는 걸 고려.

# B단계 — 라우터 / 메모리뱅크 / 봇

## 응답 경로

위에서부터 순서대로 시도한다. 위쪽일수록 싸고 빠르고 정확하다.

| 경로 | 조건 | LLM |
|---|---|---|
| `cache` | 메모리뱅크 히트 | 0회 |
| `exact` | 고유명사 정확매칭 → 저장된 완성 답변 | 0회 |
| `direct` | 벡터 상위 결과가 `VECTOR_DIRECT` 이상 | 0회 |
| `llm` | 여러 문서를 엮어야 함 | 1회 |
| `fallback` | `VECTOR_MIN` 미만 → 관리자 문의 안내 | 0회 |

정형 질문(레시피/아이템/직업)은 대부분 `exact` 에서 끝난다. **이게 토큰 절감의
핵심이고, 메모리뱅크는 그 위에서 비정형 질문의 반복을 걷어내는 보조 장치다.**

```bash
python query.py "토스파 레시피 알려줘"
python query.py --bench          # 표준 질문 12개 일괄 실행, 경로 분포 출력
python query.py -i               # 대화형
python query.py --clear-cache
```

## 의도 판별

같은 이름이 여러 DB에 있을 때(예: `치즈` = 아이템이자 레시피) 질문의 단어로 갈라낸다.

| 질문 | 의도 | 결과 |
|---|---|---|
| 치즈 어떻게 만들어 | recipe | 재료 2개, 조리대 |
| 치즈 얼마에 팔려 | item | 판매가 40골드 |
| 치즈 | 없음 | **둘 다 답변** |

의도가 안 잡히면 되묻지 않고 답할 수 있는 만큼(최대 3개) 전부 보여준다.
정말 근거가 없을 때만 관리자 문의로 넘긴다.

키워드는 `config.INTENT_RULES` 에 있다. 운영하면서 실제 질문 로그를 보고
계속 채워야 하는 부분이다.

## 메모리뱅크가 유사도만 믿지 않는 이유

마인크래프트 도메인에서는 임베딩 유사도만으로 캐시를 히트시키면 **반드시 사고가 난다.**

```
"요리사 토마토스파게티 레시피"  vs  "요리사 크림스파게티 레시피"   → 0.96+
"워리어 전직 조건"             vs  "어세신 전직 조건"            → 0.97+
```

문장 구조가 같고 고유명사 한 단어만 다르기 때문이다. 그래서 캐시 히트에
**고유명사 집합(`entity_key`) 완전 일치**를 필수 조건으로 건다.

`entity_key` 는 별칭 사전으로 찾아낸 **페이지 ID**를 정렬해 이어붙인 값이다.
표기가 달라도(`토스파` vs `토마토 스파게티`) 같은 페이지면 같은 키가 되고,
비슷하게 생긴 다른 대상이면 반드시 달라진다.

의도도 함께 본다. `치즈 레시피`와 `치즈 얼마`는 고유명사가 같아도 답이 달라야 하므로
캐시를 공유하지 않는다.

## 캐시 무효화

`sync.py` 가 동기화를 마칠 때마다 `change_log` 를 읽어, 바뀐 페이지를 근거로
만들어진 캐시를 지운다. 이걸 빼먹으면 레시피가 패치돼도 봇이 예전 답을 계속 낸다.

## 디스코드 봇

```bash
python bot.py
```

1. https://discord.com/developers/applications → New Application
2. **Bot** → Reset Token → `.env` 의 `DISCORD_TOKEN`
3. **Bot → Privileged Gateway Intents → MESSAGE CONTENT INTENT 켜기**
4. **OAuth2 → URL Generator** → `bot`, `applications.commands` 체크
   → 권한은 `Send Messages`, `Embed Links`, `Read Message History`
5. 생성된 URL로 서버에 초대

반응 방식 두 가지:

- `/거북 <질문>` — 어디서든
- 지정 채널에 그냥 쓰기 — `BOT_CHANNEL_IDS` 에 채널 ID 등록 (봇 멘션도 항상 동작)

디스코드는 상호작용에 3초 안에 응답하지 않으면 실패 처리하므로 `defer()` 로
먼저 시간을 번다. 엔진은 동기 코드라 `asyncio.to_thread` 로 넘기고, SQLite
동시 접근은 락으로 막는다.

## 임계값 튜닝

`.env` 의 네 값이 봇 품질을 좌우한다. 지금 값은 **실제 질문 로그가 없는 상태의
임시값**이라 반드시 조정해야 한다.

| 값 | 기본 | 올리면 | 내리면 |
|---|---|---|---|
| `VECTOR_MIN` | 0.32 | 모른다는 답이 늘어남 | 엉뚱한 답이 늘어남 |
| `VECTOR_DIRECT` | 0.58 | LLM 호출·비용 증가 | 요약 그대로 나가 어색할 수 있음 |
| `CACHE_SIM` | 0.94 | 캐시 적중률 하락 | 오답 위험 증가 |

`python query.py --bench` 로 현재 데이터에서의 유사도 분포를 볼 수 있다.
운영 초기에는 `VECTOR_MIN` 을 조금 높게 잡아 **틀린 답보다 모른다는 답이 나오게**
하는 편이 안전하다. 게임 정보는 틀리면 유저가 바로 알아채고 신뢰가 무너진다.
